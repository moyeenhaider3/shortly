<interfaces>
Express validation to reproduce (backend/src/service/user.service.ts `createUser`, in this exact order; the first failing check wins):

| Rank | Check | HTTP | code | message |
|------|-------|------|------|---------|
| 1 | name (trimmed), email (trimmed, lowercased) or password missing/empty/not-a-string-for-name-and-email | 400 | VALIDATION_ERROR | Name, email, and password are required |
| 2 | name length not 2..50 (after trim) | 400 | VALIDATION_ERROR | Name must be between 2 and 50 characters |
| 3 | email does not match `/^\w+([.-]?\w+)*@\w+([.-]?\w+)*(\.\w{2,3})+$/` | 400 | VALIDATION_ERROR | Please provide a valid email address |
| 4 | password not a string, or shorter than 6 | 400 | WEAK_PASSWORD | Password must be at least 6 characters long |
| 5 | role not one of ADMIN, NORMAL | 400 | INVALID_ROLE | Role must be one of: ADMIN, NORMAL |

Notes: Express uses its own regex, not a generic "is email" rule; copy the regex, do not use `@IsEmail`. A falsy password (empty string, 0) is rank 1; a truthy non-string password (e.g. 123456789) is rank 4. Public signup (Phase 4) ignores any `role` and forces NORMAL, so Phase 4 will derive a signup DTO from this one; do not do that now.
</interfaces>

<concepts>
- Pipes (transform/validate before the handler) and `ValidationPipe`; Express equivalent: manual checks in services.
- DTO classes with decorators (`class-validator`) and `class-transformer` (`@Transform`, `transform: true` to get a real class instance).
- `whitelist: true` (strip unknown properties) versus `forbidNonWhitelisted`.
- `exceptionFactory`: converting `ValidationError[]` into our own exception; the `context` option on decorators (arrives in `ValidationError.contexts`) as the way to attach `code` and priority to each rule.
- Global registration in `main.ts` (`useGlobalPipes`) versus the `APP_PIPE` token used for the filter in 02-01.
</concepts>

  <action>
    Mentor explains: what a DTO is, how class-validator decorators work, why `ValidationError` normally yields Nest's own `{statusCode,message[],error}` shape (which Flutter cannot read), and the `context` trick used here to keep Express's `code` and ordering declarative instead of scattering `if`s.
    Developer creates `CreateUserDto` with fields `name`, `email`, `password`, `role` (role typed with a string union or an enum value list of `ADMIN`, `NORMAL`), using the table in `<interfaces>`:
    - name: `@Transform` trims strings; `@IsString()` and `@IsNotEmpty()` carry rank 1 (code VALIDATION_ERROR, message `Name, email, and password are required`); `@Length(2, 50)` carries rank 2 (message `Name must be between 2 and 50 characters`).
    - email: `@Transform` trims and lowercases strings; `@IsString()` and `@IsNotEmpty()` rank 1; `@Matches(<Express EMAIL_REGEX>)` rank 3 (message `Please provide a valid email address`).
    - password: `@IsNotEmpty()` rank 1; `@IsString()` and `@MinLength(6)` rank 4 (code `WEAK_PASSWORD`, message `Password must be at least 6 characters long`). No transform: passwords are never trimmed.
    - role: `@IsIn(['ADMIN','NORMAL'])` rank 5 (code `INVALID_ROLE`, message `Role must be one of: ADMIN, NORMAL`).
    Each decorator receives `{ message: <text>, context: { code: <code>, rank: <n> } }` as its validation options (per LIFE-04, codes and messages per Express).
    Developer creates `validationExceptionFactory(errors: ValidationError[]): AppException`. It walks every error (and `children` if present), and for each failed constraint name reads `error.contexts?.[constraintName]` for `{code, rank}` and `error.constraints[constraintName]` for the message; it picks the entry with the lowest `rank` and returns `new AppException(message, 400, code)`. If no entry carries a context (an unmapped constraint), it falls back to `AppException(<first constraint message>, 400, 'VALIDATION_ERROR')`. Never include the rejected value in the message (passwords).
    Mentor's breakdown covers: `@Transform` params (`value`), why `@IsString` shares rank 1 on name/email but rank 4 on password, how `contexts` is keyed by constraint name, and why `Array` sort by `rank` gives Express's first-failure behaviour.
    File map to deliver: `create-user.dto.ts` is imported by the demo controller now and later by the users/auth controllers; `validation-exception.factory.ts` imports `AppException` (02-01) and is passed to `ValidationPipe` in Task 3; the thrown AppException is formatted by `AllExceptionsFilter`.
  </action>
