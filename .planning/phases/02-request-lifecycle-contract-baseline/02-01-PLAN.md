<objective>
Reproduce Express's error envelope in Nest: an `AppException` class (counterpart of `AppError`) and one global `@Catch()` exception filter (counterpart of `errorHandler`) that is the single place where error responses are shaped.

Purpose: every later phase just `throw new AppException(...)` and the client receives the exact Express body. Also the first contact with Nest's request lifecycle (exceptions layer).
Output: two files under `backend-nest/src/common/`, a temporary `DemoModule` used to exercise the filter, and the filter registered in `AppModule`.
</objective>

<interfaces>
Express contract being reproduced (backend/src/middlewares/error.middleware.ts):
- `AppError(message: string, statusCode: number, code: string = 'INTERNAL_ERROR')`, with `isOperational = true`.
- `errorHandler`: AppError is "client safe" and is reported as-is. Anything else is a server bug: status 500, code `INTERNAL_SERVER_ERROR`, message `Something went wrong on the server`; the original error is only `console.error`-ed.
- Response body is always exactly `{ success: false, message, code }`.

Existing Nest baseline (Phase 1): `AppModule` imports `ConfigModule.forRoot(...)` and `HealthModule`; `main.ts` does `NestFactory.create(AppModule)`.
</interfaces>
</context>

<concepts>
- Nest request lifecycle: middleware, guards, interceptors, pipes, controller, then exception filters (the exceptions layer wraps everything). Express equivalent: the 4-argument error middleware registered last.
- `HttpException` and why `AppException` extends it (Nest already knows how to read `getStatus()`).
- `@Catch()` with no argument catches everything; `ArgumentsHost` and `host.switchToHttp()` to reach the underlying Express `req`/`res`.
- Global registration two ways: `app.useGlobalFilters(new X())` (no DI) vs the `APP_FILTER` provider token (DI-aware). This plan uses `APP_FILTER`.
- Nest's `Logger` instead of `console.error`.
</concepts>

  <action>
    Mentor explains: exception filters, why `@Catch()` with no arguments, `ArgumentsHost`/`switchToHttp()`, and that this single class replaces Express's `errorHandler`.
    Developer creates `AllExceptionsFilter implements ExceptionFilter`, decorated with `@Catch()`, with `catch(exception: unknown, host: ArgumentsHost)`. It obtains the Express `Request`/`Response` types from `express` (already a dependency through `@nestjs/platform-express`; types from `@types/express`). Resolution rules, in order:
    1. `exception instanceof AppException`: status = `exception.getStatus()`, code = `exception.code`, message = `exception.message` (parity with Express AppError).
    2. Any other `HttpException` with status below 500: status = `getStatus()`, message from the exception (string response or its `message` field), code `BAD_REQUEST` (Express's default when no code or type exists). Plan 02-02 refines this branch for 404 and JSON parse errors; leave a short comment saying so.
    3. Everything else (non-HttpException, or HttpException with status 500 or above): status 500, code `INTERNAL_SERVER_ERROR`, message `Something went wrong on the server`.
    Unexpected cases (rule 3) are logged with `new Logger(AllExceptionsFilter.name)` using `.error` with the method, `request.originalUrl` and the exception's `stack` (when it is an Error). The response is sent with `response.status(status).json({ success: false, message, code })`. The body must contain exactly those three keys and never a stack or the original error message.
    Mentor's breakdown covers: `@Catch()`, `unknown` instead of `any`, `getStatus()`/`getResponse()`, why the 500 branch hides the original message (security: internals leak), `Logger` versus `console.error`.
    File map to deliver: the filter imports `AppException` (Task 1); it is registered in `app.module.ts` (Task 3); Express counterpart is `errorHandler` in `error.middleware.ts`.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> API | Any request may trigger an unexpected exception; the response body is the only thing the client sees |
| app -> server log | Stack traces and internals are allowed here, but must not cross to the client |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|

| T-02-02 | I | Nest default exception responses | mitigate | Global `@Catch()` filter replaces Nest's default `{statusCode,message,error}` shape, so framework internals and `error` names never reach clients |
| T-02-03 | R | Unexpected errors without a record | mitigate | Rule 3 logs method, URL and stack via `Logger.error` so failures are traceable server-side |
