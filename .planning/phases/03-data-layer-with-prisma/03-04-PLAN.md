<interfaces>
Verified in a scratch project on 2026-10-16 (Prisma 7.10.1 + `@prisma/adapter-pg`): an interactive transaction `await prisma.$transaction(async (tx) => { await tx.url.update({ where: { id }, data: { clickCount: { increment: 1 } } }); throw new Error('boom'); })` rejects with the thrown error and `clickCount` stays 0 afterwards (rolled back).

Contract to implement:
- `recordVisit(urlId: string, meta: { ip?: string; userAgent?: string }, options?: { failAfterIncrement?: boolean }): Promise<{ clickCount: number; visitId: string }>`
- Steps inside the callback, in this order, using ONLY the `tx` client: (1) `tx.url.update({ where: { id: urlId }, data: { clickCount: { increment: 1 } }, select: { clickCount: true } })`; (2) if `options?.failAfterIncrement` and `NODE_ENV !== 'production'`, `throw new Error('Simulated failure after increment')` (marked `// TEMPORARY: rollback experiment, removed in Phase 4 with src/demo/`); (3) `tx.visit.create({ data: { urlId, ip: meta.ip ?? null, userAgent: meta.userAgent ?? null }, select: { id: true } })`; return `{ clickCount, visitId }`.
- A nonexistent `urlId` makes step 1 throw Prisma error P2025 ("record to update not found") before anything is written; mapping that to a 404 `URL_NOT_FOUND` belongs to Phase 5, here it surfaces as the generic 500 envelope.
- Prisma behaviour to teach: `$transaction([op1, op2])` (batch/sequential form) vs `$transaction(async (tx) => ...)` (interactive form); interactive transactions have a default timeout (5 s) and hold a pooled connection, so keep them short and never make network calls inside; the nested `tx` is a client bound to the transaction's connection, the outer `this.prisma` is NOT part of it.
- Express shape reminder (Phase 5 will pass these): `ip` from `x-forwarded-for` or the socket, `userAgent` from the header, 'Unknown' defaults are an app-level choice.
- Existing wiring to respect: `DemoModule` declares `DemoController` only; `PrismaModule` is global (03-02), so `VisitsModule` must NOT import it; ValidationPipe is global with `whitelist: true`.
- Seeded data exists after 03-03; a link row is created by SQL in the commands below because there is no URL endpoint until Phase 5.
</interfaces>
</context>

<concepts>
- ACID, atomicity in particular: why two writes to two tables need a transaction while Mongo's single-document `$inc`+`$push` did not.
- Prisma interactive transactions: callback form, the `tx` client, automatic rollback on throw / commit on return, isolation default (Read Committed in Postgres), timeouts.
- Atomic increments (`{ increment: 1 }` compiles to `SET "clickCount" = "clickCount" + 1`) vs lost updates from read-modify-write.
- Prisma known-request error `P2025`; how unexpected errors reach the global filter as 500.
- A feature module that depends on the global PrismaModule without importing it; module exports (`VisitsModule` exports `VisitsService`).
- Experiment-driven learning: deliberately breaking code (wrong client inside the callback) to see partial writes.
</concepts>

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-03-15 | T | Partial write between counter and history | mitigate | Single interactive `$transaction` with `tx` for both writes; rollback proven by psql checks and the deliberate-bug experiment |
| T-03-16 | T | SQL injection through urlId or headers | mitigate | Only Prisma's parameterised query API is used (no raw SQL in the service); `ParseUUIDPipe` rejects malformed ids before the service runs; the only hand-written SQL is the developer's own psql commands |
